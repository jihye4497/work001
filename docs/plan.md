# 오늘 뭐 담지? 작업 계획서

> 상태: 착수 전 · 문서 버전 1.0 · 기준: MVP 개발 기획서 v1.0
> 위치: `docs/plan.md` · 목표: 1인 개발, 개발 시작 후 4주 내 공개 테스트 **(가정)**
> 이 문서는 완료 체크와 진행 기록으로 다음 작업을 결정한다. `docs/style_guide.md`, `docs/wireframe.md`는 추후 작성하며, 존재할 때만 참조한다.

## 1. 한눈에 보기

- **한 줄 소개:** 마트 전단지·온라인 쇼핑몰에서 발견한 관심 식재료와 기존 선택 메뉴의 공통 재료를 활용할 요리를 추천하고, 메뉴별 필요량을 합산해 재료 중심 장보기 목록을 만드는 무료 웹사이트.
- **타겟 사용자:** 국내에서 스마트폰으로 여러 마트 할인 정보를 확인하며 일주일치 장보기를 계획하는 요리 초보자. 대표 페르소나 31세 사무직 1인 가구, 주 1~3회 계획 **(가정)**.
- **결과물 유형:** 로그인·DB·결제 없는 모바일 우선 반응형 광고형 웹사이트.
- **목표 출시일:** 달력상 날짜 미정; 개발 시작일로부터 4주 내 공개 테스트 **(가정)**.
- **수익 모델·가격:** 무료 0원 + 향후 Google AdSense 광고. 승인 전에는 광고 없이 운영.
- **핵심 사용자 시나리오:** 검색으로 방문 → 처음 한 번 `기본 설정`에서 `기본 식사 인원`·`기본 추천 방식` 선택(오징어·팽이버섯·양파·감자 예시 확인) → 마트 1을 보고 팽이버섯·양파 `재료 선택`, `메뉴 추천`에서 메뉴 2개 담기 → 마트 2를 보고 `재료 선택`으로 돌아와 오징어·감자 추가(기존 메뉴 유지) → `메뉴 추천`에서 방식 전환·메뉴 추가·`조리 횟수` 수정 → `장보기 목록`에서 카테고리별 총량과 사용 메뉴 확인, 구매 체크 → 페이지 이동·재방문해도 목록 유지. 최종 구매 여부와 구매 포장 단위는 사용자가 판단.

## 2. 확정 사항

### 기술 스택

| 기술 | 역할 |
|---|---|
| HTML5 | 각 페이지의 구조 (`.html`) |
| CSS3 | 모바일 우선 반응형 디자인 |
| JavaScript ES Modules | 재료 선택·추천·계산·화면 상호작용 |
| JSON (`ingredients.json`, `recipes.json`) | 공통 식재료·레시피 데이터 |
| localStorage | 같은 브라우저의 기본 설정·장보기 작업 자동 저장 |
| GitHub | 소스 코드 및 변경 이력 관리 |
| Cloudflare Pages | 정적 웹사이트 배포 |
| Google AdSense | 추후 광고 운영(승인 전 코드 삽입 강제하지 않음) |
| Google Search Console / 네이버 서치어드바이저 | 검색 등록·색인 점검 |
| 방문자 분석 도구(미정) | 방문·화면 이동 검증 |
| Codex | 단계별 코드 작성과 테스트 보조 |

### 만드는 것: Must 7개

1. **기본 설정:** `기본 식사 인원`(1~4명 **가정**), `기본 추천 방식` 저장 및 오징어·팽이버섯·양파·감자 기준 설명·예시. `세 가지 모두 비교`는 추천 화면에서 세 가지 탭을 전환하는 의미.
2. **재료 선택:** 카테고리별 빠른 선택 버튼, 표준 식재료 자동완성, 복수 선택·추가·삭제. 수량·할인 여부·보유 여부 입력 없음. 등록되지 않은 이름 임의 등록·치환 금지.
3. **메뉴 추천:** 같은 검증 레시피 데이터를 세 가지 평가 방식(재료 최대 활용형/추가 재료 최소형/여러 끼 식단형)으로 정렬. 관심 식재료와 기존 메뉴의 공통 일반 재료 고려, 기본 양념 제외. 처음 8개와 8개씩 더 보기, 추천 이유 표시, 메뉴 선택 시 재계산.
4. **선택 메뉴 관리:** 메뉴 담기·삭제, 기본 `조리 횟수` 1회, 상단 `선택 메뉴`를 눌러 횟수 변경. 동일 레시피 중복 등록 금지. 모든 메뉴에 `기본 식사 인원` 적용, 메뉴별 별도 인분 수정 없음.
5. **장보기 목록:** 메뉴별 필요량 합산, 각 식재료에 총량·사용 메뉴·메뉴별 수량 표시, 채소·버섯/육류·해산물/두부·계란·기타/양념·조미료 구분, 체크·복사. 같은 `Ingredient.id`와 같은 단위만 합산; 다른 단위는 나란히 표시; 수량이 없으면 `수량 미기재`.
6. **화면 자유 이동:** `재료 선택` ↔ `메뉴 추천` ↔ `장보기 목록` 직접 왕복. 식재료 수정·추천 방식 변경에도 기존 `선택 메뉴`, 횟수, 작업 상태 유지.
7. **장보기 자동 저장:** localStorage로 새로고침·재방문 복원. `새 장보기 시작` 선택과 확인 후에만 현재 장보기 작업 초기화, `기본 설정`은 유지.

### 만들지 않는 것: Later·제외

- 개인 레시피 저장(`오징어볶음 - 내 레시피`), 개인 레시피 우선 추천, 유튜브 설명·댓글 텍스트 AI 분석.
- 웹·앱 동기화, 모바일 앱, 회원가입, 인증, 서버 DB, 결제·구독, 이메일 발송, 클라우드 저장, 사용자 파일 업로드.
- 전단지 OCR, 쇼핑몰 실시간 가격·판매 포장 단위 비교, AI 개인화 식단·영양 분석, 유튜브 API·영상 삽입·일반 메뉴 유튜브 연결.
- AI가 존재하지 않는 레시피를 생성하는 기능, 원문 계량 단위의 임의 g·mL 변환, 냉장고 재고 관리, 할인·보유 재료 구분.

### 출시 후 추가할 것: Nice

- 메뉴 상세 정보(재료량·간단한 조리 설명).
- 이번 장보기에서만 장보기 수량 직접 보정(원본 레시피 변경 금지).
- 최근 사용 식재료 우선 노출.
- 계량 단위 안내(1T=15mL, 1t=5mL, 밥숟가락은 일정한 표준 없음; 모두 부피 안내이며 재료별 g 환산은 하지 않음).

- 최초 경로: `홈 → 기본 설정 → 재료 선택 → 메뉴 추천 → 장보기 목록`.
- 반복 사용: `재료 선택 ↔ 메뉴 추천 ↔ 장보기 목록`의 상단 내비게이션으로 자유 이동. `기본 설정`은 별도 설정 버튼으로 언제든 이동.
- `메뉴 추천`과 `장보기 목록` 모두 상단에 `선택 메뉴` 표시; 메뉴 버튼 클릭 시 `조리 횟수` 변경.
- 관심 재료 추가·삭제는 추천 후보에만 영향을 주며, 이미 담은 메뉴를 자동 삭제하지 않는다.
- 빈 상태, 데이터 로딩 실패, 저장 실패, 손상된 저장 데이터, 없는 추천 후보, 404에 각각 안내 메시지를 표시한다.
- 광고 예정 위치: 홈 하단 1, 메뉴 추천 목록 하단 1, 장보기 목록 하단 1, 가이드 본문 하단 1 **(가정)**. 설정·재료 선택·정책 페이지는 광고 없음. 광고 승인은 필수 출시 조건이 아님.

## 5. 데이터 구조

**저장 방식:** 서버 DB 없음. `data/*.json` 공통 읽기 전용 데이터 + localStorage 브라우저별 장보기 상태.

| 저장 위치 | 데이터 이름 | 필드 | 타입 | 필수/설명 |
|---|---|---|---|---|
| `data/ingredients.json` | `Ingredient` | `id` | string | 필수; 변하지 않는 재료 ID |
| 동일 | `Ingredient` | `name` | string | 필수; 표준 재료명 |
| 동일 | `Ingredient` | `aliases` | string[] | 동의어·자동완성 검색어 |
| 동일 | `Ingredient` | `category` | string | 필수; 장보기 카테고리 |
| 동일 | `Ingredient` | `isSeasoning` | boolean | 필수; 추천 점수에서 제외할 양념 표시 |
| 동일 | `Ingredient` | `isQuickPick` | boolean | 빠른 선택 노출 여부 |
| `data/recipes.json` | `Recipe` | `id` | string | 필수; 변하지 않는 레시피 ID |
| 동일 | `Recipe` | `name` | string | 필수; 메뉴명 |
| 동일 | `Recipe` | `baseServings` | number | 필수; 기준 인분, 양수 |
| 동일 | `Recipe` | `servingsStatus` | string/생략 | 사용자 승인 변경: `estimated`는 1인분 추정; 생략 또는 `explicit`는 기존 기준 유지 |
| 동일 | `Recipe` | `servingsEvidence` | string/생략 | `estimated`일 때 필수; 원문 미표기·검토한 재료량·추정 근거 기록 |
| 동일 | `Recipe` | `cookMinutes` | number/null | 조리 시간 |
| 동일 | `Recipe` | `cookingType` | string | 필수; 국·찌개·볶음 등 |
| 동일 | `Recipe` | `imagePath` | string/null | 이미지 경로 또는 없음 |
| 동일 | `Recipe` | `ingredients` | `RecipeIngredient[]` | 필수; 레시피의 각 재료 |
| 동일 | `Recipe` | `sourceNote` | string | 출처·검수 메모 |
| `Recipe.ingredients[]` | `RecipeIngredient` | `ingredientId` | string | 필수; `Ingredient.id` 참조 |
| 동일 | `RecipeIngredient` | `amount` | number/null | 원문 기준 수량, 불명확하면 null |
| 동일 | `RecipeIngredient` | `unit` | string/null | g, 개, 마리, T 등 원문 단위 |
| 동일 | `RecipeIngredient` | `note` | string/null | 듬뿍, 크기 등 메모 |
| `localStorage: jmd_settings_v1` | `UserSettings` | 기본 식사 인원, 기본 추천 방식 | JSON object | 최초 설정 후 재사용 |
| `localStorage: jmd_draft_v1` | `ShoppingDraft` | `schemaVersion`, `selectedIngredientIds`, `selectedRecipes`, `activeRecommendationMode`, `checkedIngredientIds` | JSON object | 현재 장보기; `selectedRecipes[]`는 `recipeId`, `times` 포함 |
| `localStorage: jmd_meta_v1` | `StorageMeta` | 스키마 버전, 마지막 저장 시각 | JSON object | 저장·복원 관리 |

**관계:** `Ingredient` ↔ `Recipe`는 `RecipeIngredient`를 통한 N:M. `ShoppingDraft` → `selectedRecipes`는 1:N, `ShoppingDraft` → `Ingredient`는 관심 ID 배열을 통한 N:M. 장보기 총량은 별도 영구 저장하지 않고 파생 계산.

**계산:** `최종 필요량 = 레시피 기준 수량 × 기본 식사 인원 ÷ baseServings × times`.

- 사용자 승인(2026-11-10)에 따라 인분 미표기 메뉴는 재료량을 항목별로 대조한 뒤 `1인분 기준(추정)`으로 반영할 수 있다. 열량만으로 인분을 확정하거나 전체 미표기 메뉴를 자동으로 1인분 처리하지 않는다. 추정 여부를 메뉴 추천·선택 메뉴·장보기 목록·복사 결과에 유지한다. 판단이 어려운 원문은 보류한다.

- 같은 `ingredientId`와 **같은 단위**인 수량끼리만 합산; `1.5마리 + 200g`처럼 다른 단위는 분리.
- `T`·`t`·`밥숟가락`은 서로 다른 단위로 유지, 자동 g 환산 금지.
- `amount === null`은 `수량 미기재`로 표시하고 0으로 덮어쓰지 않는다.
- `isSeasoning`이 true면 추천의 공통 재료 점수에서 제외하지만 장보기 목록에는 포함.
- 추천 로직: 검증된 레시피 후보만 사용. 관심 식재료 1개면 해당 재료 요리, 2개면 공통 활용 우선+개별 허용, 3개 이상이면 다중 관심 재료 활용 우선+개별 허용. `재료 최대 활용형`은 관심/공통 활용, `추가 재료 최소형`은 새 일반 재료 종류 최소, `여러 끼 식단형`은 조리 유형 다양성 우선. 가중치·동점 기준은 조정 가능한 초기값 **(가정)**; 동점이면 관심 재료 활용 수, 그다음 메뉴명 순 **(가정)**.
- localStorage는 현재 도메인·브라우저에만 저장. 다른 기기 동기화 없음. 저장값은 사용 전 유효성 확인하고 이상한 데이터는 안내 후 안전 복구.
- 원본 JSON은 브라우저가 수정하지 않는다. 개인정보(이름·전화번호 등)는 저장하지 않으며, DOM 삽입 시 사용자 입력을 HTML 코드로 실행하지 않는다.

  - 완료 기준: 추천 카드에 활용 관심 재료와 공유 재료가 사실대로 표시된다.
  - 확인 방법: 오징어볶음을 담은 뒤 양파를 공유하는 후보에 근거 설명이 나오는지 확인한다.
- [ ] **5-3. `추가 재료 최소형` 점수 구현**
  - 할 일: 관심 재료+선택 메뉴 재료 집합에 없는 일반 식재료 종류 수를 최소화.
  - 완료 기준: 새로운 일반 식재료 종류가 적은 후보가 우선하며 기존 보유 여부를 아는 것처럼 표현하지 않는다.
  - 확인 방법: 공통 재료가 많은 후보와 새 재료가 많은 후보의 순위를 비교한다.
- [ ] **5-4. `여러 끼 식단형` 점수 구현**
  - 할 일: 기존 선택 메뉴와 조리 유형이 다른 후보 우선, 관심·공통 재료도 고려.
  - 완료 기준: 볶음만 담았을 때 국·찌개·조림 등 다른 유형이 우선될 수 있다.
  - 확인 방법: 볶음 메뉴 선택 후 해당 탭으로 바꾸어 순위 확인.
- [ ] **5-5. 추천 방식 전환 및 선택 변경 갱신**
  - 할 일: 세 가지 탭 전환, `기본 추천 방식` 반영, 메뉴 추가·삭제·관심 재료 변경 시 재계산. `세 가지 모두 비교` 설정은 탭 전환 제공으로 처리.
  - 완료 기준: 기존 선택 메뉴·횟수는 그대로이고 추천 순위만 변한다.
  - 확인 방법: 같은 관심 재료에서 세 탭을 번갈아 누르고 메뉴 추가 후 다시 비교한다.
- [ ] **5-6. 8개 및 `더 보기` 표시**
  - 할 일: 최초 최대 8개, 클릭마다 다음 최대 8개 표시. 추천 조건이 바뀌면 첫 8개로 복귀.
  - 완료 기준: 후보 수 미만 표시와 마지막 더 보기 숨김이 정확하다.
  - 확인 방법: 8개 초과 후보에서 더 보기 및 후보 소진 상태 확인.
- [ ] **5-7. 추천 알고리즘 자동 테스트**
  - 할 일: 양념 제외, 관심 재료 개수별 후보, 중복 선택 제외, 동점 결정, 세 모드 순위·이유의 일관성 검사.
  - 완료 기준: 테스트 통과 및 후보 부족 안내가 작동한다.
  - 확인 방법: 테스트 실행, 검색 후보 없음 상태를 직접 열어본다.

여기까지 되면: 메뉴를 하나 담을 때마다 다음 메뉴 추천이 달라지고 세 방식으로 비교할 수 있다.

## 8. AI 작업 규칙

1. **항상 작업 시작 전에 `docs/plan.md`를 읽어라.** 우선순위는 7절에서 가장 앞에 있는 미완료 체크박스다. 사용자가 별도로 지정한 작업이 있으면 그 작업의 범위만 수행하라.
2. **한 번에 체크박스 하나만 진행하라.** 시작 전에 작업 목표·수정 예상 파일·직접 확인 방법을 간단히 알리고, 끝난 뒤 테스트 결과·바뀐 파일·사용자가 누를 위치를 알려라. 완료 기준 충족 후 해당 체크박스만 `[x]`로 바꿔라.
3. 매 작업 종료 시 10절 **진행 기록**에 날짜, 한 일, 다음에 할 일을 한 줄 추가하라. 구현 전 작업을 완료 표시하지 마라. 실패·미확인은 그대로 남겨라.
4. **만들지 않는 것** 및 현재 단계 외 기능을 임의 추가하지 마라. 필요해 보이는 변경은 구현하지 말고 먼저 사용자에게 물어라.
5. `docs/style_guide.md`와 `docs/wireframe.md`가 존재하면 **화면 작업 전 반드시 읽고** 준수하라. 파일이 없다고 추측해 작성하거나 작업을 중단하지 마라.
6. HTML + CSS + JavaScript ES Modules + JSON + localStorage 기술 범위를 지켜라. 승인 없이 프레임워크·서버·DB·빌드 시스템·외부 API를 새로 설치하거나 도입하지 마라.
7. 데이터의 `Ingredient.id`, `Recipe.id`, `UserSettings`, `ShoppingDraft`, `RecipeIngredient` 등 확정된 이름과 저장 키(`jmd_settings_v1`, `jmd_draft_v1`, `jmd_meta_v1`)를 일관되게 유지하라.
8. 레시피 원본 단위와 `baseServings`를 보존하라. **동일 ID·동일 단위만 합산**하고, 모르는 수량·단위를 임의 생성·변환하지 마라. 수량 계산과 추천 점수는 DOM 화면 코드와 분리하고 가능한 경우 자동 테스트하라.
9. 메뉴를 담거나 관심 재료·추천 방식을 바꾸어도 이미 담은 메뉴 및 `조리 횟수`를 지우지 마라. 장보기 초기화는 사용자 확인이 있을 때만 수행하고 `기본 설정`은 유지하라.
10. 기본 양념은 추천 점수에서 제외하되 `장보기 목록`에는 남겨라. 추천 이유는 계산 가능한 사실만 말하고, 가격 절감·보유 여부를 추정해 단정하지 마라.
11. 사용자 입력과 외부 데이터는 검증하고 문자열을 HTML 코드로 실행하지 마라. API 키·토큰·암호 등 비밀 값을 소스 파일이나 Git에 기록하지 마라.
12. 새 작업 시 먼저 기존 코드와 테스트를 확인하고 최소 수정만 적용하라. 완료 후 해당 기능을 직접 재현하는 단계와 자동 테스트 결과를 보고하라.
13. `[직접]` 항목은 사용자에게 필요한 클릭·승인·계정 행동을 설명하되 사용자의 실제 실행 없이 완료 체크하지 마라.
