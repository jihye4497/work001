### 메뉴 재료 자동 연결·디자인 정리 승인 (2026-11-11)

- 선택한 메뉴의 집에 없는 일반 재료를 관심 재료에 자동 연결한다. 양념은 관심 버튼에 자동 추가하지 않지만 구매/보유 장보기에는 모든 수량을 반영한다. 기존에 담은 메뉴도 로딩 후 연결한다.
- ShoppingDraft의 선택적 manualIngredientIds:string[]는 직접 고른 재료, suppressedAutoIngredientIds:string[]는 사용자가 자동 관심 표시를 해제한 재료다. 이전 저장값은 기존 선택 재료를 직접 선택으로 간주해 보존한다. 자동 재료는 selectedRecipes와 부위 대체·보유 여부에서 다시 계산한다.
- 메뉴 삭제 시 다른 메뉴가 사용하는 자동 재료·직접 선택한 재료는 유지하고 그 메뉴에만 필요한 자동 재료를 제거한다. 자동 관심 표시를 해제해도 실제 메뉴에 필요한 장보기 재료는 제거하지 않는다.
- 사용자가 자동 재료를 검색에서 다시 직접 고르면 직접 선택으로 보존한다. 보유 여부 수정·새로고침·횟수·메뉴 변경 후 같은 규칙을 적용한다. 새 장보기는 출처 상태도 초기화한다.
- 홈 반복 설명과 별도 가이드 강조를 줄이고 추천 방식 설명은 선택 펼침으로 둔다. 추천 카드에는 메뉴명·기준 인분·담기만 우선 보이고 자세한 이유는 ⋯에 유지한다. 검색·종류·선택·장보기 기능은 유지한다.

### 최신 승인 보완 (2026-11-11)

아래 이전 배치·양념 점수 제외 규칙과 충돌하면 이 절을 우선한다.
- 홈은 사용 안내와 확정 문구·추천 방식 설명·재료 선택 이동을 제공한다. 보유 재료 입력은 홈에서 제거하고 재료 선택의 집에 있는 재료/새로 살 관심 재료 두 탭으로 통합한다. 기본 탭은 보유 재료이며 ?tab=planned 또는 ?tab=pantry로 직접 접근한다. 선택 화면의 안내 문단은 제거한다.
- 추가 구매 최소는 관심 선택 버튼을 숨긴다. 구매 예정 일반 재료와 보유 일반 재료의 합집합 중 하나 이상을 사용하는 메뉴를 찾는다. 구매 예정 재료가 없어도 보유 재료로 추천한다. 모두 비어 있으면 후보를 생성하지 않는다.
- 추가 구매 최소는 activeInterestIds를 읽지 않으며 관심 활용 모드에서의 선택을 변경하지 않는다. 이 모드의 extra에는 보유·구매 예정에 없는 양념도 포함한다. 다른 동점 규칙·원본 수량·부위 대체 정책은 유지한다.
- 관심 재료 활용만 활성 관심 재료 버튼과 전체 포함 조건을 적용한다. 선택한 재료가 없으면 빈 상태다. 보유 여부와 구매 예정 여부의 장보기 구분은 유지한다.
- 음식 종류는 두 모드 모두 항상 표시하며 가로 스크롤 한 줄·다중 선택이다. 추천 방식 안내 펼침은 없애고 홈 설명으로 옮긴다.

### 최신 사용자 승인 범위 (2026-11-11)


추가 승인(2026-11-11): 아래 초기 배치와 충돌하면 다음을 우선한다. 기능은 유지하고 정보 표시 순서·펼침 구조를 변경한다.
- 홈 식사 인원은 미설정일 때만 표시하고 이후 기본 설정에서 바꾼다. 소개는 제목·짧은 문구·단계 아이콘 중심으로 압축한다.
- 보유/구매 예정 재료는 검색·선택 요약 펼침·한 번에 한 카테고리로 표시한다. 전체 재료 검색·저장·수정 기능은 유지한다.
- 추천 화면은 검색 → 두 방식 → 관심 재료 → 음식 종류 펼침 → 2열 결과 순이다. 방식 설명은 별도 펼침이다. 선택 메뉴는 하단 확인 영역으로 이동하고 최초 3개·더 보기·횟수 편집을 제공한다.
- 선택 메뉴는 한 줄 목록이며 −/횟수/+가 항상 보인다. 삭제·대체 근거는 ⋯에서 연다. 긴 이름과 기준 인분은 필요하면 같은 행 안에서 줄바꿈한다.
- 장보기는 구매할 재료와 집에 있는 재료 두 구획이다. 양념도 보유 선택 여부로 구분하고 양념 표식을 붙인다. 자동 보유 처리하지 않는다. 복사에도 같은 두 구획·모든 항목을 반영한다.
- 재료 체크박스는 구매 체크만 바꾸고, 재료명·총량 버튼은 사용 내역 펼침만 바꾼다. 보유 재료 전체는 기본 접힘·전체 너비 펼침 행이다. 식사 인원·조리 횟수 변경 및 구매 체크 시 펼침 상태를 유지한다.
- 새 장보기 버튼의 위치·동작은 이번에 바꾸지 않는다.

이 절은 아래 초기 기획 중 충돌하는 흐름·세 추천 방식·보유 재료 제외 결정을 대체한다. 원본 데이터 수량·단위·기술 스택·기존 12개 화면은 유지한다.

- 홈에서 `기본 식사 인원` 1~4명과 `집에 있는 재료`를 고른다. 보유량은 받거나 차감하지 않는다. 다음 `재료 선택`은 새로 살 재료다. 기존 선택 메뉴는 유지한다.
- 추천 방식은 `추가 구매 최소`, `관심 재료 활용` 두 개다. 기본은 추가 구매 최소다. 새로 살 재료를 관심 재료 버튼으로 표시하고 각각 선택·해제한다.
- 추가 구매 최소: 활성 관심 재료를 하나 이상 쓰는 메뉴 중 보유+구매 예정 재료 외 일반 재료 수 오름차순 → 보유 활용 수 내림차순 → 주재료 활용 수 내림차순이다.
- 관심 재료 활용: 활성 관심 재료 모두를 사용하는 메뉴만 표시한다. 주재료 활용 수 내림차순 → 보유 활용 수 내림차순 → 추가 구매 수 오름차순이다. 두 방식 모두 동점이면 부위 대체 수 오름차순 → 메뉴명 → ID 순이다. 양념은 점수에서 제외하며 관련 없는 메뉴로 8개를 강제 채우지 않는다.
- 주재료 판정은 현재 메뉴명·재료명·동의어와 명시된 대표 메뉴 규칙으로 실행 시 계산한다. 무게 비율로 임의 판정하지 않는다. 전 메뉴 수작업 검수 완료를 뜻하지 않으며 오분류는 후속 검토한다.
- 전체 메뉴 검색은 이름으로 찾으며 관심 재료·음식 종류·추천 제외와 무관하게 전체 등록 메뉴에서 검색한다. 이미 담은 메뉴는 담김으로 표시한다. 검색을 지우면 이전 추천 조건을 적용한다.
- 음식 종류 다중 선택·제외 관리·8개씩 더 보기는 유지한다. 모바일 추천 카드는 2열이다. 실제 이미지 없는 카드는 이미지 공간을 만들지 않는다.
- 장보기 목록은 `구매할 재료 / 집에 있는 재료 / 양념·조미료` 순이다. 총량 오른쪽, 아래 사용 메뉴·현재 식사 인원·횟수·계산량을 표시한다. 복사는 같은 구획·총량을 사용한다. 보유량 차감·소스 분리 계산은 하지 않는다.
- 돼지 목살/목심은 같은 부위로 연결한다. 김치찌개에서만 돼지 앞다리살·목살·삼겹살 사이 대체를 허용한다. 다른 축종·다짐육·다른 요리 부위는 자동 치환하지 않는다. 담을 때 실제 사용할 부위 ID를 저장하고 장보기에 그 부위로 합산한다.
- `jmd_recipe_preferences_v1`에 기존 `excludedRecipeIds`와 `pantryIngredientIds:string[]`를 함께 저장한다. 둘 다 새 장보기 후 유지한다. `ShoppingDraft`에 `activeInterestIds:string[]`, `menuQuery:string`(최대 200자)를 저장하고 초기화 시 비운다. `selectedRecipes[]`의 선택적 `ingredientReplacements`는 원본 재료 ID → 사용할 재료 ID다.
- 예전 저장값은 메뉴·횟수를 보존한다. 재료 최대 활용형은 관심 재료 활용으로, 나머지 옛 방식은 추가 구매 최소로 복원한다. 활성 재료 필드가 없는 옛 값은 구매 예정 재료 전체를 활성화한다.
- 조리 순서·레시피 상세창은 이 구현에 포함하지 않는다. 원문 명시 인분과 사용자 확인 인분 정책 및 1,033개 메뉴는 그대로 유지한다.

## 1. 한눈에 보기

- **한 줄 소개:** 마트 전단지·온라인 쇼핑몰에서 발견한 관심 식재료와 기존 선택 메뉴의 공통 재료를 활용할 요리를 추천하고, 메뉴별 필요량을 합산해 재료 중심 장보기 목록을 만드는 무료 웹사이트.
- **타겟 사용자:** 국내에서 스마트폰으로 여러 마트 할인 정보를 확인하며 일주일치 장보기를 계획하는 요리 초보자. 대표 페르소나 31세 사무직 1인 가구, 주 1~3회 계획 **(가정)**.
- **결과물 유형:** 로그인·DB·결제 없는 모바일 우선 반응형 광고형 웹사이트.
- **목표 출시일:** 달력상 날짜 미정; 개발 시작일로부터 4주 내 공개 테스트 **(가정)**.
- **수익 모델·가격:** 무료 0원 + 향후 Google AdSense 광고. 승인 전에는 광고 없이 운영.
- **핵심 사용자 시나리오:** 검색으로 방문 → 홈에서 `기본 식사 인원`·`집에 있는 재료` 선택 → 마트 1을 보고 팽이버섯·양파 `재료 선택`, `추천 메뉴`에서 메뉴 2개 담기 → 마트 2를 보고 `재료 선택`으로 돌아와 오징어·감자 추가(기존 메뉴 유지) → `추천 메뉴`에서 방식 전환·메뉴 추가·`조리 횟수` 수정 → `장보기 목록`에서 카테고리별 총량과 사용 메뉴 확인, 구매 체크 → 페이지 이동·재방문해도 목록 유지. 최종 구매 여부와 구매 포장 단위는 사용자가 판단.

### 만드는 것: Must 7개

1. **기본 설정:** `기본 식사 인원`(1~4명 **가정**), `기본 추천 방식` 저장 및 오징어·팽이버섯·양파·감자 기준 설명·예시. `세 가지 모두 비교`는 추천 화면에서 세 가지 탭을 전환하는 의미.
2. **재료 선택:** 카테고리별 빠른 선택 버튼, 표준 식재료 자동완성, 복수 선택·추가·삭제. 수량·할인 여부 입력 없음. 보유 여부는 홈에서 별도로 선택한다. 등록되지 않은 이름 임의 등록·치환 금지.
3. **추천 메뉴:** 같은 검증 레시피 데이터를 세 가지 평가 방식(재료 최대 활용형/추가 재료 최소형/여러 끼 식단형)으로 정렬. 관심 식재료와 기존 메뉴의 공통 일반 재료 고려, 기본 양념 제외. 처음 8개와 8개씩 더 보기, 추천 이유 표시, 메뉴 선택 시 재계산.
4. **선택 메뉴 관리:** 메뉴 담기·삭제, 기본 `조리 횟수` 1회, 상단 `선택 메뉴`를 눌러 횟수 변경. 동일 레시피 중복 등록 금지. 모든 메뉴에 `기본 식사 인원` 적용, 메뉴별 별도 인분 수정 없음.
5. **장보기 목록:** 메뉴별 필요량 합산, 각 식재료에 총량·사용 메뉴·메뉴별 수량 표시, 채소·버섯/육류·해산물/두부·계란·기타/양념·조미료 구분, 체크·복사. 같은 `Ingredient.id`와 같은 단위만 합산; 다른 단위는 나란히 표시; 수량이 없으면 `수량 미기재`.
6. **화면 자유 이동:** `재료 선택` ↔ `추천 메뉴` ↔ `장보기 목록` 직접 왕복. 식재료 수정·추천 방식 변경에도 기존 `선택 메뉴`, 횟수, 작업 상태 유지.
7. **장보기 자동 저장:** localStorage로 새로고침·재방문 복원. `새 장보기 시작` 선택과 확인 후에만 현재 장보기 작업 초기화, `기본 설정`은 유지.

### 만들지 않는 것: Later·제외

- 개인 레시피 저장(`오징어볶음 - 내 레시피`), 개인 레시피 우선 추천, 유튜브 설명·댓글 텍스트 AI 분석.
- 웹·앱 동기화, 모바일 앱, 회원가입, 인증, 서버 DB, 결제·구독, 이메일 발송, 클라우드 저장, 사용자 파일 업로드.
- 전단지 OCR, 쇼핑몰 실시간 가격·판매 포장 단위 비교, AI 개인화 식단·영양 분석, 유튜브 API·영상 삽입·일반 메뉴 유튜브 연결.
- AI가 존재하지 않는 레시피를 생성하는 기능, 원문 계량 단위의 임의 g·mL 변환, 냉장고 수량 재고 관리, 할인 입력. 보유 여부 구분은 최신 승인 범위로 포함한다.

### 출시 후 추가할 것: Nice

- 메뉴 상세 정보(재료량·간단한 조리 설명).
- 이번 장보기에서만 장보기 수량 직접 보정(원본 레시피 변경 금지).
- 최근 사용 식재료 우선 노출.
- 계량 단위 안내(1T=15mL, 1t=5mL, 밥숟가락은 일정한 표준 없음; 모두 부피 안내이며 재료별 g 환산은 하지 않음).

## 5. 데이터 구조

### 사용자 승인 변경: 음식 종류·추천 제외·모바일 압축 (2026-11-10)

- `data/recipe-categories.json`의 `entries[]`에 `recipeId`, 검토한 `name`, `categories[]`, `mealRole`을 저장한다. 레시피 수량·출처 데이터는 유지하며 새 메뉴 추가 시 분류를 함께 검토한다. 분류는 서비스 탐색용 편집 판단이며 음식 기원을 확정하는 정보가 아니다.
- 음식 종류는 `한식 주메뉴`, `한식 반찬`, `한식 국·찌개`, `양식`, `일식`, `중식`, `그 밖`, `퓨전`을 사용한다. 한식 밥·면·죽은 주메뉴에 포함한다. 역할이 겹치는 한식은 주메뉴·반찬 양쪽에 포함한다.
- `ShoppingDraft.selectedFoodCategories: string[]`는 다중 선택을 저장한다. 빈 배열은 전체다. 선택한 종류의 합집합에 기존 세 추천 방식을 적용하고 동일 메뉴는 한 번만 보여준다. 인분·조리 횟수·선택 메뉴는 필터 변경으로 지우지 않는다. 기존 v1 저장값에 필드가 없으면 빈 배열만 보완한다.
- `localStorage: jmd_recipe_preferences_v1`은 `{schemaVersion:1, excludedRecipeIds:string[]}`를 저장한다. 제외는 추천 후보에만 적용하며 기존 선택 메뉴는 유지한다. `새 장보기 시작`·기본 설정 변경으로 제외 목록을 지우지 않는다.
- 추천 카드의 `⋯`에서 제외하고 실행 취소를 제공한다. 기본 설정의 `제외한 메뉴 관리`에서 검색·10개씩 더 보기·개별 복원·전체 복원을 제공한다. 전체 복원은 확인 후 수행한다. 관리창을 닫아도 저장 전 기본 설정 입력값은 유지한다.
- 모바일 상단 메뉴를 고정하고 `1명 · 설정`처럼 인원을 한 번만 표시한다. 선택 메뉴는 `메뉴명 · 기준 인분 ×횟수`로 압축하고 처음 3개와 전체 펼치기를 제공한다. 카드의 인분 경고 상자를 보조 글자로 바꾸되 추정 여부는 유지한다. 레시피 상세·조리 순서 추가는 이번 범위에 포함하지 않는다.

**저장 방식:** 서버 DB 없음. `data/*.json` 공통 읽기 전용 데이터 + localStorage 브라우저별 장보기 상태.

**관계:** `Ingredient` ↔ `Recipe`는 `RecipeIngredient`를 통한 N:M. `ShoppingDraft` → `selectedRecipes`는 1:N, `ShoppingDraft` → `Ingredient`는 관심 ID 배열을 통한 N:M. 장보기 총량은 별도 영구 저장하지 않고 파생 계산.

**계산:** `최종 필요량 = 레시피 기준 수량 × 기본 식사 인원 ÷ baseServings × times`.

- 사용자 직접 확인·승인(2026-11-11)에 따라 검수해 반영한 인분 미표기 메뉴는 `user-confirmed`·1인분 기준으로 계산하고 화면·합산·복사에는 추정 문구를 붙이지 않는다. 원문에 명시된 인분을 우선하며, 내부에는 확인 날짜와 사용자 확인 기준을 남겨 공식 원문 검증과 구분한다. 기존 추정 근거는 검수 기록의 `previousServingsEvidence`에 보존한다. 재료 목록·단위·메뉴명이 해석되지 않는 원문은 인분과 별개의 사유로 보류한다.

- 같은 `ingredientId`와 **같은 단위**인 수량끼리만 합산; `1.5마리 + 200g`처럼 다른 단위는 분리.
- `T`·`t`·`밥숟가락`은 서로 다른 단위로 유지, 자동 g 환산 금지.
- `amount === null`은 `수량 미기재`로 표시하고 0으로 덮어쓰지 않는다.
- `isSeasoning`이 true면 추천의 공통 재료 점수에서 제외하지만 장보기 목록에는 포함.
- 추천 로직: 검증된 레시피 후보만 사용. 관심 식재료 1개면 해당 재료 요리, 2개면 공통 활용 우선+개별 허용, 3개 이상이면 다중 관심 재료 활용 우선+개별 허용. `재료 최대 활용형`은 관심/공통 활용, `추가 재료 최소형`은 새 일반 재료 종류 최소, `여러 끼 식단형`은 조리 유형 다양성 우선. 가중치·동점 기준은 조정 가능한 초기값 **(가정)**; 동점이면 관심 재료 활용 수, 그다음 메뉴명 순 **(가정)**.
- localStorage는 현재 도메인·브라우저에만 저장. 다른 기기 동기화 없음. 저장값은 사용 전 유효성 확인하고 이상한 데이터는 안내 후 안전 복구.
- 원본 JSON은 브라우저가 수정하지 않는다. 개인정보(이름·전화번호 등)는 저장하지 않으며, DOM 삽입 시 사용자 입력을 HTML 코드로 실행하지 않는다.

**환경변수:** MVP 필수 환경변수 **없음**. 인증·결제·이메일·AI API·서버 DB 사용 안 함. 광고 게시자 ID 등은 승인 후 확인된 값만 적용. 필요한 비밀 값이 미래에 생기면 저장소에 올리지 않고 배포 플랫폼의 비밀 설정에 저장한다. 현재 `.env` 생성·사용을 강제하지 않는다.

**비용:** Cloudflare Pages·GitHub 무료 플랜으로 먼저 시도; 도메인·Codex 구독비 별도 확인. 월 운영 예산 3만 원 이하 **(가정)**, 실제 결제 전 사용자 확인.

## 7. 작업 단계

아래 체크박스의 초기 세 모드·최초 기본 설정 흐름은 상단 최신 승인 범위로 대체한다. 직접 확인하지 않은 배포·모바일·외부 계정 항목은 완료 처리하지 않는다.

> 실행 지침: **한 번에 체크박스 하나**를 작업한다. 작업 시작 시 `docs/plan.md`에서 가장 앞의 미완료 항목을 골라 진행한다. 4주 일정은 **(가정)**이고 배포·검증과 광고 승인은 별도다. 각 단계 마지막의 체험은 바로 확인 가능해야 한다.

### 단계 4. 재료 중심 장보기 목록 (2주 차 후반·가정)

목표: 선택 메뉴의 재료를 실제 필요량으로 계산하고 구매 체크한다.

  - 할 일: `amount × 기본 식사 인원 ÷ baseServings × times` 계산을 UI와 분리하여 작성.
  - 완료 기준: 메뉴 횟수를 2회로 설정하면 해당 메뉴 필요량이 2배가 된다.
  - 확인 방법: 오징어볶음 1회·2회의 오징어·양파 수량 비교 및 테스트 실행.
- [ ] **4-2. 동일 재료·동일 단위 합산 구현**
  - 할 일: `ingredientId`·`unit`별 합산; 서로 다른 단위는 따로 표시하고 수량 미기재는 유지.
  - 완료 기준: `1.5마리 + 200g`이 억지 환산되지 않고 표시된다.
  - 확인 방법: 오징어 단위가 다른 레시피 두 개를 담아 확인한다.
- [ ] **4-3. `장보기 목록` 카테고리 및 메뉴별 사용량 표시**
  - 할 일: 4개 카테고리 순서로 식재료 총량·사용 메뉴·각 메뉴의 필요량 표시. 양념도 목록에 포함.
  - 완료 기준: 재료가 중심이고, 어떤 메뉴에 들어가는지 각 항목 아래 보인다.
  - 확인 방법: 오징어볶음·오징어찌개를 담고 양파 항목 아래 두 메뉴가 표시되는지 확인한다.
- [ ] **4-4. 장보기 목록 상단 `선택 메뉴` 편집 연결**
  - 할 일: 목록 상단 메뉴 버튼 클릭으로 조리 횟수 조정, 합산 즉시 갱신.
  - 완료 기준: 다른 화면으로 가지 않고 횟수 조정 가능.
  - 확인 방법: 목록 상단 오징어볶음 1→2회 조정 후 오징어 총량 확인.
- [ ] **4-5. 구매 체크·목록 복사 구현**
  - 할 일: 재료별 구매 체크 및 텍스트 복사 기능. 체크해도 항목 삭제·숨김 금지.
  - 완료 기준: 체크 표시가 바뀌고 복사된 텍스트에 카테고리·재료·수량이 포함된다.
  - 확인 방법: 양파 체크, 목록 복사 후 메모장에 붙여넣기.
- [x] **4-6. 계산 자동 테스트 작성**
  - 할 일: 인분 환산·횟수·같은 단위·다른 단위·수량 미기재·양념 분류 테스트.
  - 완료 기준: 해당 테스트가 모두 통과한다.
  - 확인 방법: README에 문서화한 테스트 명령 실행 후 결과 확인.

여기까지 되면: 식재료별 총량과 사용 메뉴를 보여주는 실제 장보기 체크리스트를 작성할 수 있다.

### 단계 5. 추천 메뉴 (최신 승인 범위 적용) (3주 차 초반·가정)

목표: 현재 관심 식재료와 기존 메뉴에 따라 추천 순위가 달라진다.

- [ ] **5-1. 검증된 후보 레시피 선정 함수 작성**
  - 할 일: 관심 식재료를 활용하는 후보를 찾고 이미 담은 레시피 제외; 관심 재료 1·2·3개 이상 규칙 적용.
  - 완료 기준: 각 입력 개수에서 관련 후보만 반환되며 없는 요리는 생성하지 않는다.
  - 확인 방법: 오징어 1개, 오징어+감자 2개, 오징어+감자+양파 3개를 차례로 선택한다.
- [ ] **5-2. `재료 최대 활용형` 점수 및 추천 이유 구현**
  - 할 일: 관심 재료 여러 개 사용과 기존 메뉴의 주요 재료 공유 우선; 기본 양념 제외.
  - 완료 기준: 추천 카드에 활용 관심 재료와 공유 재료가 사실대로 표시된다.
  - 확인 방법: 오징어볶음을 담은 뒤 양파를 공유하는 후보에 근거 설명이 나오는지 확인한다.
- [ ] **5-3. `추가 재료 최소형` 점수 구현**
  - 할 일: 관심 재료+선택 메뉴 재료 집합에 없는 일반 식재료 종류 수를 최소화.
  - 완료 기준: 새로운 일반 식재료 종류가 적은 후보가 우선하며 기존 보유 여부를 아는 것처럼 표현하지 않는다.
  - 확인 방법: 공통 재료가 많은 후보와 새 재료가 많은 후보의 순위를 비교한다.
- [ ] **5-4. `여러 끼 식단형` 점수 구현**
  - 할 일: 기존 선택 메뉴와 조리 유형이 다른 후보 우선, 관심·공통 재료도 고려.
  - 완료 기준: 볶음만 담았을 때 국·찌개·조림 등 다른 유형이 우선될 수 있다.
  - 확인 방법: 볶음 메뉴 선택 후 해당 탭으로 바꾸어 순위 확인.
- [ ] **5-5. 추천 방식 전환 및 선택 변경 갱신**
  - 할 일: 세 가지 탭 전환, `기본 추천 방식` 반영, 메뉴 추가·삭제·관심 재료 변경 시 재계산. `세 가지 모두 비교` 설정은 탭 전환 제공으로 처리.
  - 완료 기준: 기존 선택 메뉴·횟수는 그대로이고 추천 순위만 변한다.
  - 확인 방법: 같은 관심 재료에서 세 탭을 번갈아 누르고 메뉴 추가 후 다시 비교한다.
- [ ] **5-6. 8개 및 `더 보기` 표시**
  - 할 일: 최초 최대 8개, 클릭마다 다음 최대 8개 표시. 추천 조건이 바뀌면 첫 8개로 복귀.

  - 확인 방법: 테스트 실행, 검색 후보 없음 상태를 직접 열어본다.

여기까지 되면: 메뉴를 하나 담을 때마다 다음 추천 메뉴이 달라지고 세 방식으로 비교할 수 있다.

## 8. AI 작업 규칙

1. **항상 작업 시작 전에 `docs/plan.md`를 읽어라.** 우선순위는 7절에서 가장 앞에 있는 미완료 체크박스다. 사용자가 별도로 지정한 작업이 있으면 그 작업의 범위만 수행하라.
2. **한 번에 체크박스 하나만 진행하라.** 시작 전에 작업 목표·수정 예상 파일·직접 확인 방법을 간단히 알리고, 끝난 뒤 테스트 결과·바뀐 파일·사용자가 누를 위치를 알려라. 완료 기준 충족 후 해당 체크박스만 `[x]`로 바꿔라.
3. 매 작업 종료 시 10절 **진행 기록**에 날짜, 한 일, 다음에 할 일을 한 줄 추가하라. 구현 전 작업을 완료 표시하지 마라. 실패·미확인은 그대로 남겨라.
4. **만들지 않는 것** 및 현재 단계 외 기능을 임의 추가하지 마라. 필요해 보이는 변경은 구현하지 말고 먼저 사용자에게 물어라.
5. `docs/style_guide.md`와 `docs/wireframe.md`가 존재하면 **화면 작업 전 반드시 읽고** 준수하라. 파일이 없다고 추측해 작성하거나 작업을 중단하지 마라.
6. HTML + CSS + JavaScript ES Modules + JSON + localStorage 기술 범위를 지켜라. 승인 없이 프레임워크·서버·DB·빌드 시스템·외부 API를 새로 설치하거나 도입하지 마라.
7. 데이터의 `Ingredient.id`, `Recipe.id`, `UserSettings`, `ShoppingDraft`, `RecipeIngredient` 등 확정된 이름과 저장 키(`jmd_settings_v1`, `jmd_draft_v1`, `jmd_meta_v1`)를 일관되게 유지하라.
8. 레시피 원본 단위와 `baseServings`를 보존하라. **동일 ID·동일 단위만 합산**하고, 모르는 수량·단위를 임의 생성·변환하지 마라. 수량 계산과 추천 점수는 DOM 화면 코드와 분리하고 가능한 경우 자동 테스트하라.
9. 메뉴를 담거나 관심 재료·추천 방식을 바꾸어도 이미 담은 메뉴 및 `조리 횟수`를 지우지 마라. 장보기 초기화는 사용자 확인이 있을 때만 수행하고 `기본 설정`은 유지하라.
10. 기본 양념은 추천 점수에서 제외하되 `장보기 목록`에는 남겨라. 추천 이유는 계산 가능한 사실만 말하고, 가격 절감·보유 여부를 추정해 단정하지 마라.
11. 사용자 입력과 외부 데이터는 검증하고 문자열을 HTML 코드로 실행하지 마라. API 키·토큰·암호 등 비밀 값을 소스 파일이나 Git에 기록하지 마라.
12. 새 작업 시 먼저 기존 코드와 테스트를 확인하고 최소 수정만 적용하라. 완료 후 해당 기능을 직접 재현하는 단계와 자동 테스트 결과를 보고하라.
13. `[직접]` 항목은 사용자에게 필요한 클릭·승인·계정 행동을 설명하되 사용자의 실제 실행 없이 완료 체크하지 마라.
